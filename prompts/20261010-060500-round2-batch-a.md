## Key decisions

**Two 500s hid behind "should return an error" probes.** The weak
`assert resp.status_code in (400, 500, 501)` family was exactly what the
review flagged — deterministic client errors were being answered with
real 500s. Driving the requests captured the two shapes:

1. A JSON-protocol call with NO X-Amz-Target dispatched an unrelated
   moto handler and died with KeyError('TableName') → the bridge now
   answers 400 InvalidAction up front.
2. A body that json cannot decode crashed moto's handler from inside
   (KeyError, since moto's parser handed it a partial body). The bridge
   now decodes it itself and answers 400 ValidationException.

The suite's assertions were then PINNED to those deterministic statuses
in the same tests (no spilled-500 coverage-gap disguise), and the
diag-header assertion in the compat file is now unconditional.

`werkzeug.exceptions.NotFound` (what `MapAdapter.match` raises) and
`NoMatch` in the catch set — both routing-miss exceptions carve the 501
gap contract away from 500-class dispatch crashes.
